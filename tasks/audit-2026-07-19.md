# Codebase Audit — winner-app

**Date:** 2026-07-19
**Method:** Layered audit (7 layers), parallel per-layer review, evidence-gated. Every finding cites `file:line` with quoted code and a concrete failure scenario. Speculative/style-only items were dropped. All Critical findings and the load-bearing High findings were re-read against source (marked ✓ verified).
**Categories:** BUG · BOTTLENECK · FRAMEWORK-FIGHT · BEST-VIOLATION (includes security).

> Scope note: `texting.js`, `settings.js`, `selection.js` persistence findings are consolidated under Layer 4 (they live in app-logic modules); Layer 3 covers `database.js`/`session.js` only. Cross-layer duplicates (e.g. the collections read-modify-write race in routes + service) are noted where they recur.

## Layer 1 — Backend API (`server.ts`, `middleware.ts`, `config.ts`, `routes/*.ts`)

### [BEST-VIOLATION][Critical] server.ts:33-34,41,93-94 — `/win/api/*` reaches every API route with no auth or rate limit ✓ verified
- **Details:** `sessionAuth`/`generalLimiter` are registered as `app.use('/api', …)` so they only match paths starting `/api`. The whole `mainRouter` is mounted at both `/` and `/win` (`app.use('/win', mainRouter)`), so `/win/api/winners` skips both guards, then matches `/win`, strips the prefix, and enters `apiRouter`.
- **Justification:** Any unauthenticated, unthrottled client gets full GET/POST/PUT/DELETE on all collections plus MP/texting endpoints via the `/win/api/*` path.
- **Fix:** Attach `sessionAuth`/`generalLimiter` inside `apiRouter` (`mainRouter.use('/api', sessionAuth, generalLimiter, apiRouter)`) so the guard travels with the router under every mount point.

### [BEST-VIOLATION][High] mp.ts:37-38,335 — user input concatenated unescaped into MinistryPlatform filter strings ✓ verified
- **Details:** `filter = \`… AND Event_Title LIKE '%${searchTerm}%'\`` and the templating `filter.replace(new RegExp(\`{{${key}}}\`,'g'), String(value))` interpolate `req.body` values into the MP REST `filter` clause with no escaping.
- **Justification:** A `searchTerm` of `' OR 1=1 --` alters server-side query semantics — query-language injection reachable by any operator (and anyone through the `/win/api` bypass).
- **Fix:** Whitelist/parameterize filter values, or escape single quotes and reject filter metacharacters before building the clause.

### [BEST-VIOLATION][High] middleware.ts:44-51 + auth.ts:73 — rate limiting off unless `NODE_ENV` is exactly `production`; `/login` has no strict limiter
- **Details:** `const isDev = process.env.NODE_ENV !== 'production'; max: isDev ? 0 : 100, skip: () => isDev`; `/login` is mounted without `strictLimiter`.
- **Justification:** A process deployed without `NODE_ENV=production` disables all rate limiting; even when enabled, `/login` is only under the 100/min general limiter, leaving the single shared admin password open to brute force.
- **Fix:** Require an explicit config flag to disable limits (fail-fast on unknown env), and apply `strictLimiter` to `/login`.

### [BUG][High] collections.ts:136,164 — PUT and DELETE ignore the `writeCollection` boolean and always report success ✓ verified
- **Details:** Both handlers `await writeCollection(...)` then unconditionally `res.json({ success: true, … })`; `writeCollection` returns `false` on EACCES/ENOENT instead of throwing (service layer, see L2).
- **Justification:** A silently failed persist still returns `{ success: true }`; the client believes the edit/delete saved when it did not. (POST and batch-save do check.)
- **Fix:** Check the boolean and respond 500 on `false` — or better, make `writeCollection` throw (see L2 fix).

### [BUG][High] collections.ts:74-104, batch.ts:88-105 — unsynchronized read-modify-write causes lost updates
- **Details:** Every mutation does `readCollection` → mutate whole array → `writeCollection`, with no locking. `batch.ts:50` even labels itself "atomic".
- **Justification:** Two overlapping requests to the same collection both read the pre-change array; the second write overwrites the first, dropping a record. Same root cause as the service-layer race in L2 and the frontend race in L3.
- **Fix:** Serialize writes per collection (async mutex/queue keyed by collection name) or move to a store with atomic updates.

### [BOTTLENECK][Medium] server.ts:32-34 — 50 MB JSON bodies parsed before auth/rate-limit
- **Details:** `express.json({ limit: '50mb' })` runs before `generalLimiter` and `sessionAuth`.
- **Justification:** An unauthenticated request to any public path can submit up to 50 MB that Node parses on the event-loop thread, blocking all other requests during the parse.
- **Fix:** Lower the global limit; apply the large limit only to the specific authenticated routes that need it.

### [BEST-VIOLATION][Medium] auth.ts:96 — session cookie `secure` flag depends on unset-defaulting `NODE_ENV`
- **Details:** `secure: process.env.NODE_ENV === 'production'`.
- **Justification:** A production process missing `NODE_ENV=production` issues the session cookie without `Secure`, allowing transmission over plain HTTP.
- **Fix:** Drive `secure` from an explicit validated config flag, not an implicit env default.

### [BEST-VIOLATION][Low] reports-proxy.ts:9-22 — client-controlled path forwarded with the operator's Authorization header
- **Details:** `req.params[0]` is concatenated into `https://tickets.revival.com/reports/${reportPath}…` and `Authorization: req.headers.authorization` is forwarded.
- **Justification:** `../` segments in the path reach arbitrary paths on the upstream host while carrying the forwarded credentials.
- **Fix:** Validate `reportPath` against an allowed prefix/pattern and reject traversal before building the URL.

### [BUG][Low] mp.ts:26-27 — `daysPast || 7` overrides a legitimate `0` ✓ verified
- **Details:** `const pastDays = daysPast || 7;` while the guard at line 39 is `daysPast !== undefined`.
- **Justification:** A request sending `daysPast: 0` passes the guard but is coerced to 7, silently widening the date window.
- **Fix:** Use `daysPast ?? 7` / `daysFuture ?? 30`.

### [BEST-VIOLATION][Low] auth.ts:88 — password compared with non-constant-time `===`
- **Details:** `if (username === validUser && password === validPass)`.
- **Justification:** `===` short-circuits on the first differing byte, leaking timing information about the correct password.
- **Fix:** Compare with `crypto.timingSafeEqual` over fixed-length hashed buffers.

### [BEST-VIOLATION][Low] middleware.ts:65-145 — `authErrorPage` HTML constant is dead code
- **Details:** ~80-line HTML string defined but never referenced (`sessionAuth` returns JSON errors).
- **Justification:** Unused maintenance weight.
- **Fix:** Remove it, or wire it into the 401 response if an HTML page is intended.

## Layer 2 — Backend services (`collection.ts`, `mp-service.ts`, `texting.ts`, `texting-scheduler.ts`, `upload.ts`)

### [BUG][Critical] collection.ts:85-97 — non-atomic fallback write can destroy the live collection file on I/O failure ✓ verified
- **Details:** On any temp-write/rename error the code falls back to `await fs.writeFile(filePath, …)` directly on the real `${collection}.json`, defeating the temp+rename safety above it.
- **Justification:** Under ENOSPC (or a crash mid-write) the direct `writeFile` truncates the target file and then fails — the original data is destroyed, exactly what the atomic path exists to prevent.
- **Fix:** Remove the fallback; propagate the error from the atomic path (fail fast, never write the target non-atomically).

### [BEST-VIOLATION][High] upload.ts:13,24-30 + server.ts:44 — upload filter trusts client mimetype and stores the client extension; files are served back from the app origin ✓ verified
- **Details:** `fileFilter` accepts on `file.mimetype.startsWith('image/')` (client-supplied header) and the filename keeps `path.extname(file.originalname)`; `mainRouter.use('/uploads', express.static(UPLOADS_DIR))` serves the result.
- **Justification:** An authenticated user uploads `x.html` declared `image/png`, stored as `background-<ts>.html` and served as `text/html` from the app origin — stored XSS. `.svg` (scriptable) also passes the filter legitimately.
- **Fix:** Validate magic bytes server-side (file-type/sharp), derive a whitelisted safe raster extension from the detected type (never `originalname`), and serve `/uploads` with `X-Content-Type-Options: nosniff` / `Content-Disposition`.

### [BUG][High] collection.ts:44-48 — corrupted `settings.json` silently becomes `[]`, and the next save erases all settings
- **Details:** `if (collection === 'settings') { … return []; }` on parse failure, while every other collection throws.
- **Justification:** After corruption, `readCollection('settings')` returns `[]`; the next `POST /settings` appends one item and overwrites the file — every other setting is unrecoverably lost with no error surfaced.
- **Fix:** Throw on corrupted settings like other collections, and back up the corrupt file before any recovery.

### [BUG][High] collection.ts:65,73 — no write serialization + shared temp path; concurrent writers lose updates and hit the destructive fallback
- **Details:** All callers read-all → mutate → write-all, and every write to a collection uses the same fixed `.${collection}.json.tmp`.
- **Justification:** Two concurrent writers last-write-win (dropping a record); the loser's `rename` can also fail `ENOENT` on the shared temp name and drop into the non-atomic fallback above.
- **Fix:** Per-collection in-process mutex/queue plus a unique temp filename per write.

### [BUG][High] texting.ts:266-267 — report responses without a `delivery` object are never handled; job polls forever
- **Details:** `const delivery = result.data?.delivery; if (delivery) { … }` with no `else`; `getMessageReport` never throws on non-OK HTTP.
- **Justification:** A 401/404/5xx/non-JSON report skips the whole block — `status` stays `queued`, `nextCheckAt` stays stale, and the 2-minute cron reselects the job forever; the `retryCount >= 10` caps live only inside the `delivery`/`catch` branches and are never reached.
- **Fix:** Treat `!result.success || !delivery` as a retry-with-backoff case using the existing max-retry logic.

### [BUG][High] texting.ts:149,153 — jobs file written non-atomically and parsed with no recovery
- **Details:** `writeJobs` does a bare `fs.writeFile(JOBS_FILE, …)`; `readJobs` does `JSON.parse(data)` with no guard.
- **Justification:** A crash mid-write leaves truncated JSON, after which `readJobs` throws every call — `processQueue` fails on every tick and all texting endpoints 500 until the file is repaired by hand. This re-implements the collection layer with strictly worse guarantees.
- **Fix:** Persist jobs through the shared collection layer (atomic temp+rename + guarded parse).

### [BEST-VIOLATION][High] collection.ts:100-108 — `writeCollection` swallows all errors and returns `false`
- **Details:** `catch { console.error(...); return false; }` instead of throwing.
- **Justification:** Callers (L1 PUT/DELETE) ignore the boolean and report success — the boolean-return anti-pattern instead of fail-fast.
- **Fix:** Make it `Promise<void>` that throws; let route error handlers return 500.

### [BOTTLENECK][Medium] texting.ts:198,334-336 — jobs appended forever; each pass does full read+rewrite of two files per job
- **Details:** `jobs.push(job)` with no pruning of terminal jobs; `processQueue` loops `checkJobStatus` → `updateJob` (full RW of jobs file) + `updateWinnerSmsStatus` (full RW of winners.json) per job.
- **Justification:** `texting-jobs.json` grows monotonically; each 2-minute pass costs 2N full reads and 2N full rewrites of two unbounded files for N pending jobs.
- **Fix:** Prune terminal-status jobs past a retention window; load each file once per pass, apply updates in memory, persist once.

### [BUG][Medium] texting.ts:195-199 — `updateJob` read-modify-write races between scheduler and request handlers
- **Details:** `readJobs` → `findIndex`/mutate → `writeJobs`, run unsynchronized by both HTTP `queueAndSend` and cron `checkJobStatus`.
- **Justification:** Interleaved runs build `writeJobs` from a stale array and drop the other writer's job record.
- **Fix:** Serialize all jobs-file mutations through one in-process queue/mutex.

### [BUG][Medium] texting.ts:70,109 — outbound fetch calls have no timeout/AbortSignal
- **Details:** Both `fetch(...)` calls to `a.eztexting.com` omit any timeout.
- **Justification:** A stalled connection holds each call for undici's ~300s default, hanging the `queueAndSend` request for minutes and overrunning the 2-minute cron interval (feeding the overlap/race conditions above).
- **Fix:** Pass `AbortSignal.timeout(~15s)` to both and surface the abort as a job error.

### [FRAMEWORK-FIGHT][Medium] texting-scheduler.ts:17 — cron scheduled without node-cron's `noOverlap`
- **Details:** `cron.schedule('*/2 * * * *', …)`; installed node-cron 4.5.0 exposes `noOverlap?: boolean`.
- **Justification:** When `processQueue` exceeds 2 minutes, ticks stack and overlapping runs double-poll jobs, amplifying the `updateJob` write race.
- **Fix:** Pass `{ noOverlap: true }`.

### [BEST-VIOLATION][Medium] mp-service.ts:7-10 — missing MP credentials produce warn + `null` instead of failing fast
- **Details:** `if (!process.env.MP_USERNAME || !process.env.MP_PASSWORD) { console.warn(...); return null; }`.
- **Justification:** A typo'd/absent env var boots cleanly and surfaces only as per-request nulls every caller must guard — masked until an MP feature is exercised in production.
- **Fix:** Validate MP credentials at startup and throw; keep `getMPInstance` non-nullable.

### [BUG][Low] texting.ts:320,323 — interrupted `'sending'` jobs never reconciled; the `'sending'` filter branch is dead
- **Details:** The check filter requires `j.messageId && …`, but a job persisted as `'sending'` before the send completes keeps `messageId: null`.
- **Justification:** Such a job is excluded from every check pass forever (never failed/expired, inflates the pending stat); no persisted `'sending'` job ever has a messageId, making that filter entry unreachable.
- **Fix:** On startup, mark stale `'sending'` jobs failed; drop the dead filter entry.

### [BEST-VIOLATION][Low] upload.ts:52-55 — `listUploadedImages` swallows filesystem errors and returns `[]`
- **Details:** `catch { console.error(...); return []; }`.
- **Justification:** EACCES/missing dir is returned as an empty image list, making a broken deployment indistinguishable from "no images".
- **Fix:** Propagate the error (500); treat only ENOENT as a legitimate empty result.

## Layer 3 — Frontend data layer (`database.js`, `session.js`)

### [BUG][Critical] database.js:263-275 — winner documents updated via uncoordinated read-modify-write; concurrent writers clobber fields ✓ verified
- **Details:** `getFromStore('winners', id)` → `{...existingWinner, ...updateData}` → `saveToStore('winners', …)`, with no version/ETag/field-level PATCH.
- **Justification:** During a live event the scanner persists pickups (`scan-app.js` `updateWinner(id,{pickedUp:true})`) while the SMS flow rewrites full winner docs from its own snapshot; whichever POST lands last reverts the other's field, so a pickup during a status poll is silently lost while the scanner UI shows success.
- **Fix:** Add a server-side field-level PATCH (or optimistic-concurrency version check) and route both scanner pickup and SMS status writes through it.

### [BEST-VIOLATION][High] database.js:136-137 — `getFromStore` swallows every non-401 error and returns `[]`, enabling hard-delete of a referenced list ✓ verified
- **Details:** `// Return empty array if API is unavailable` / `return []`; consumed by `isListReferenced` (387-395).
- **Justification:** A 500/network failure on GET winners/history yields `[]`, so `hasWinners`/`hasHistory` read false and `lists.js` executes `deleteFromStore('lists', id)` — permanently deleting a list that has winners/history instead of archiving it. The `[]` return also violates the `null`-on-404 contract, defeating `if (!existingWinner)` guards.
- **Fix:** Rethrow from `getFromStore` (fail fast); callers that tolerate absence handle it explicitly; the delete flow must abort on error.

### [BEST-VIOLATION][High] database.js:308-313 — `batchFetch` masks total failure as "every collection is empty"
- **Details:** On error it builds `emptyResults[req.collection] = []` for each request and returns it.
- **Justification:** `winners.js` caches these fabricated empties (pinning "no winners" in its 5s cache); `selection.js` turns the same failure into a misleading "Selected prize not found". This is precisely the class of bug `session.js` documents as fixed for 401 — still live for every other error.
- **Fix:** Remove the catch-and-fabricate block so `batchFetch` rejects; surface the failure at call sites.

### [BUG][Medium] database.js:414-426 — `initDB` returns `undefined` (not throw) when the health check is non-OK
- **Details:** `if (response.ok) { … return true; }` with the throw only in the network-exception `catch`.
- **Justification:** A 500/503 health response falls through to `undefined`, so `app.js` proceeds with full initialization against a broken backend, then degrades through the silent `[]` fallbacks.
- **Fix:** `if (!response.ok) throw …; return true;`.

### [BUG][Low] database.js:361-364 — `archiveList` archive-then-delete is non-atomic with no compensation
- **Details:** `saveToStore('archive', …)` then `deleteFromStore('lists', id)`.
- **Justification:** If the DELETE fails after the archive POST succeeds, the list exists in both stores with no rollback.
- **Fix:** A single server-side atomic archive endpoint (or delete-first, archive-on-success with compensation).

### [BUG][Low] database.js:367-375 — dead `isSharded` branch contradicted by its own comment
- **Details:** `if (list.isSharded && list.shardIds) { … }`; `isSharded` is set nowhere and line 74 says "No longer need sharding".
- **Justification:** Unreachable code that misleads readers, plus a sequential-await N+1 delete loop if ever run.
- **Fix:** Delete the branch.

### [BEST-VIOLATION][Low] database.js:33-47,164-255 — `listenToCollection`, `queryStore`, and the interval-tracking machinery are dead exports
- **Details:** ~130 lines with zero callers repo-wide.
- **Justification:** Pure maintenance surface; `queryStore` also re-downloads full collections and sorts in place (latent bottleneck).
- **Fix:** Remove all three blocks and their exports.

### [FRAMEWORK-FIGHT][Low] database.js:38-46 — unconditional `beforeunload` handler blocks bfcache for zero benefit
- **Details:** A `beforeunload` listener that clears `activeIntervals` (which timers never survive anyway).
- **Justification:** A registered `beforeunload` handler makes the page ineligible for back/forward cache in Firefox/Safari — a real navigation-speed cost with no functional effect.
- **Fix:** Delete it along with the dead polling layer.

## Layer 4 — Frontend app logic (`app.js`, `selection.js`, `winners.js`, `settings.js`, `texting.js`, `reports.js`, `export.js`, `csv-parser.js`, `validation.js`, `ministryplatform.js`, `sounds.js`)

### [BEST-VIOLATION][Critical] reports.js:11-14 — hardcoded API credentials shipped in the client bundle ✓ verified
- **Details:** `const REPORTS_AUTH = { username: 'admin', password: 'revival' }`, used to build a Basic-auth header at line 113.
- **Justification:** The reports backend credentials are readable in page source by anyone who loads the app, exposing that backend to arbitrary callers.
- **Fix:** Move authentication into the `/api/reports-proxy` server route; the browser must never hold these credentials.

### [BUG][High] reports.js:159 — `CSVParser.setPendingCSVData` is not a function; report import crashes on the main path ✓ verified
- **Details:** Call to `CSVParser.setPendingCSVData({…})`, but `csv-parser.js` exports only a `set pendingCSVData` accessor.
- **Justification:** Every report import throws `TypeError` after the data is fetched (caught, shown as a generic error toast), so "Add from Report" can never complete.
- **Fix:** Assign via the setter: `CSVParser.pendingCSVData = {…}` (as `ministryplatform.js:998` already does).

### [BUG][High] selection.js:231,497 — `preventSamePrize` exclusions are permanently deleted from the stored list
- **Details:** `originalList.entries = allEntries` (the draw-time filtered pool) is then persisted via `operations.push({ collection: 'lists', data: updatedList })`.
- **Justification:** For a single list with removal enabled, entries excluded only because they already won *this* prize are permanently removed from the list and can never win any other prize; undo restores only the selected winners, not the excluded ones.
- **Fix:** Never persist the draw-time filtered pool; fetch the stored list fresh and remove only the selected winners' entries (as the combined-list path does).

### [BUG][High] selection.js:131,170 — per-list `preventWinningSamePrize` is written but never read
- **Details:** Only the global `settings.preventSamePrize` is consulted; `csv-parser.js:668` and `lists.js:372` persist `listSettings.preventWinningSamePrize`.
- **Justification:** A list configured to keep winners in the pool (auto-setting `preventWinningSamePrize` true) awards the same prize to the same person twice whenever the global toggle is off — the per-list setting has no effect.
- **Fix:** Resolve exclusion per source list: `list.metadata.listSettings?.preventWinningSamePrize ?? settings.preventSamePrize`.

### [BUG][High] selection.js:83-84,356 — double-click on the big play button starts two concurrent draws
- **Details:** The guard checks a CSS class (`selectionControls` has `d-none`) that is only added later inside `performWinnerSelection`, after multiple awaited network calls.
- **Justification:** A second click in that window passes the guard and runs a full second selection — two winner batches and history entries are saved, and both `selectedPrize.quantity -= numWinners` writes start from the same fetched quantity, so the prize count is decremented only once for two draws.
- **Fix:** Set a synchronous in-flight flag (or disable the button) as the first statement of `handleBigPlayClick`, cleared in `finally`.

### [BUG][High] export.js:120,297 — `Settings.settings` is undefined; backups silently contain no settings
- **Details:** `settings: Settings.settings` — the module exposes `get data()`, not `settings`.
- **Justification:** Both backups serialize `settings: undefined` (dropped by JSON.stringify); on restore `if (backupData.settings)` is never true, so all theme/behavior settings are silently lost from every backup.
- **Fix:** Use `Settings.data`, plus a fail-fast assertion in `restoreBackupData` when an expected section is missing.

### [BUG][High] winners.js:102,167 — `clearAllWinners` operates on a stale snapshot of the filtered winners
- **Details:** `currentFilteredWinners` is set only inside `loadWinners`; the destructive delete reads that cached snapshot.
- **Justification:** The Alpine "Clear Filters" button changes filters reactively without firing the native `change` events that trigger a reload, so the table can display all winners while `currentFilteredWinners` still holds the previous subset — "Clear All Winners" then deletes a different set than what is shown.
- **Fix:** Read `Alpine.store('winners').filtered` live inside `clearAllWinners`.

### [BUG][High] csv-parser.js:207-211 (also ministryplatform.js:929-933, lists.js:150) — CSV/record values injected into `innerHTML` unescaped
- **Details:** Preview cells built as `\`<td>${row[header] || ''}</td>\`` and assigned to `previewBody.innerHTML`; same pattern in the MP preview and in confirmation-modal messages.
- **Justification:** A CSV cell (including data fetched from the remote reports server) containing `<img src=x onerror=…>` executes script in the admin app.
- **Fix:** Build preview cells via `createElement`/`textContent` (SafeHTML/DOMUtils already exist).

### [BUG][Medium] csv-parser.js:81 — `parseCSV` splits on `\n`, corrupting quoted fields with embedded newlines
- **Details:** `csvText.split('\n').filter(line => line.trim())`.
- **Justification:** A quoted field with an embedded newline (standard in Excel/Sheets exports) is split into two malformed rows, silently shifting columns.
- **Fix:** Parse with a single quote-aware state machine (or a proper CSV library) instead of pre-splitting.

### [BUG][Medium] export.js:29-39 — "filtered" winners export omits the date filter and diverges from the table's list matching
- **Details:** Re-implements the filter without `filterDate` and matches on `listNameMap[...]` rather than the store's enriched `w.listName`.
- **Justification:** With a date filter active the export includes all dates while claiming "Exported N filtered winners"; archived-list filters match zero rows.
- **Fix:** Export exactly `Alpine.store('winners').filtered`.

### [BUG][Medium] export.js:69-78 — CSV export does not escape embedded double quotes
- **Details:** Fields wrapped as `\`"${value}"\`` with no doubling of inner `"`.
- **Justification:** Any value containing `"` terminates the field early and shifts all subsequent columns; RFC 4180 requires doubling inner quotes.
- **Fix:** A shared `csvEscape` that applies `value.replace(/"/g, '""')` to every field.

### [BUG][Medium] validation.js:74-75 — "dangerous characters" regex matches only the literal 6-char sequence
- **Details:** ``const dangerousChars = /<>\"\'`;/;`` (no character class) tested against the name.
- **Justification:** It only matches the exact string ``<>"'`;``, so `<script>` passes `validateName`; the replacement branch shows the intent was a class `[<>…]` — the sanitization gate is dead.
- **Fix:** Use a character class: ``/[<>"'`;]/``.

### [BUG][Medium] texting.js:544-553 — `checkMessageStatus` reschedules itself forever with no attempt cap
- **Details:** `queued`/`unknown` reschedule at 10s/30s, and the `catch` reschedules at 30s, with no counter. (Flagged by both the data-layer and app-logic auditors.)
- **Justification:** A message stuck at `unknown`, or a persistently failing endpoint, polls every 10–30s per message for the page lifetime; each poll triggers a full-winners fetch/save. A bulk send of N produces N perpetual timer chains.
- **Fix:** Track attempts per messageId with exponential backoff and a hard cap; mark `unverified` when exhausted.

### [BUG][Medium] winners.js:387 — undo caller-detection via stack sniffing never matches; the guard is dead
- **Details:** `const isUndoOperation = new Error().stack.includes('undoLastSelection');`, but `resetToSelectionMode` is invoked from a modal callback after `undoLastSelection` has returned.
- **Justification:** The stack never contains that name, so the guard is always false and every undo reloads Lists and Prizes twice.
- **Fix:** Pass an explicit `{ skipStoreRefresh }` parameter instead of inspecting the stack.

### [BOTTLENECK][Medium] texting.js:237-241 — every SMS status flush downloads the entire winners collection
- **Details:** Computes `winnerIds` (never used), then `batchFetch([{ collection: 'winners' }])`.
- **Justification:** Each flush (and each delayed status check) transfers all winner documents to update a handful; grows unbounded as winners accumulate.
- **Fix:** Fetch only the affected winners by id (the batch endpoint supports it), or PATCH the `sms` field server-side.

### [BOTTLENECK][Medium] selection.js:75-76,359 — a Worker + blob URL are created per draw and never released
- **Details:** `new Worker(URL.createObjectURL(blob))` each selection; no `terminate()` / `revokeObjectURL` anywhere.
- **Justification:** Every draw leaks one worker thread plus one blob URL for the page lifetime; a long event with many draws accumulates them.
- **Fix:** `terminate()` and revoke the URL in a `finally`, or create the worker once and reuse it.

### [BOTTLENECK][Medium] selection.js:465-466 (also winners.js:279-280,300) — N+1 sequential list fetches in loops
- **Details:** `for (const listId of sourceListIds) { await getFromStore('lists', listId); }`.
- **Justification:** A combined list of K sources issues K serialized round-trips during winner-save and undo; the batched alternative is already used 350 lines earlier in the same file.
- **Fix:** Batch-fetch all source lists in one request before the loop.

### [BEST-VIOLATION][Medium] settings.js:665-819 (+ selection.js:517-568) — the countdown/overlay block is duplicated four times
- **Details:** `case 'animation' / 'swirl-animation' / 'christmas-snow'` each repeat the same overlay/interval/stop sequence, and `selection.js` has a fourth copy.
- **Justification:** The copies have already diverged — `showCountdown` supports `time-machine` but not `christmas-snow`; `showDelayDisplay` is the reverse.
- **Fix:** Extract one parameterized `runCountdownOverlay(seconds, startAnimationFn)`.

### [BEST-VIOLATION][Medium] settings.js:73-77,96-100,131-135 — server sync is fire-and-forget while the user is told "Settings saved"
- **Details:** `Database.batchSave(...).then().catch(console.error)` followed by an immediate success toast.
- **Justification:** The toast fires regardless of whether the server write succeeds; on failure localStorage and the server diverge permanently and other devices load stale values.

## Layer 7 — Build & ops (`vite.config.js`, `tsconfig*.json`, `package.json`, `Dockerfile`, `docker-compose.yml`, shell scripts, `nodemon.json`)

> Facts (missing lockfile, committed compiled JS, puppeteer download size, unmatched paths) were cross-checked with `git ls-files`/`ls`/`find`.

### [BUG][High] deploy.sh:49-57 — deploy reports success even when the build fails or the container crash-loops
- **Details:** The ssh heredoc has no `set -e` and never checks `docker-compose up -d --build`; success is decided by `docker ps | grep -q "winner-app"`.
- **Justification:** On build failure the old container (deliberately left running) still matches the grep, so the script prints "✅ Container is running" / "Deployment completed successfully" while production runs the stale build; a crash-looping ("Restarting") container also passes.
- **Fix:** `set -e` in the heredoc, fail on non-zero from the build, and verify via `docker inspect … .State.Health.Status` or a `/api/health` poll.

### [BEST-VIOLATION][High] .gitignore:8,11 + Dockerfile:13-14 — no dependency lockfile is committed; every build is unreproducible
- **Details:** Both `pnpm-lock.yaml` and `package-lock.json` are gitignored (verified untracked); the Dockerfile comments "package-lock.json may be out of sync" and runs `npm install` (not `npm ci`) in both stages.
- **Justification:** Both installs resolve semver ranges fresh on every build — two consecutive deploys can ship different dependency versions with no code change, and the builder/prod stages can resolve differently within one image.
- **Fix:** Commit `package-lock.json`, switch both installs to `npm ci`, and settle on one package manager.

### [BEST-VIOLATION][High] rebuild-docker.sh:35-55 — no `set -e`: a failed `--no-cache` build still runs `up -d` and prints "Rebuild complete!"
- **Details:** `docker-compose build --no-cache` is followed unconditionally by `docker rmi`/`up -d` and a completion message.
- **Justification:** If the build fails, `up -d` starts whatever image it can and the operator is told the rebuild succeeded.
- **Fix:** `set -euo pipefail` and check the build exit code before removing the old image or starting containers.

### [BEST-VIOLATION][Medium] deploy.sh:23-30 — rsync of the working tree without `--delete` and without excluding gitignored compiled backend JS
- **Details:** The rsync excludes `node_modules`/`.git`/`data`/`dist`/`.env` but not `backend/**/*.js|map` (17 gitignored compiled files, verified); `.dockerignore` doesn't exclude them either, and the Dockerfile `COPY`s them.
- **Justification:** Without `--delete`, sources deleted locally persist on the server forever and get recompiled into future images; deploys reflect one developer's uncommitted working tree, not the repository.
- **Fix:** Deploy from git (clone/pull or a CI-built image), or add `--delete` plus `backend/**/*.js|map` excludes and a separate compiled `outDir`.

### [BOTTLENECK][Medium] package.json:43 + Dockerfile:14 — puppeteer devDependency downloads ~500 MB of Chrome in every uncached builder install, for a script the build never runs
- **Details:** puppeteer's postinstall downloads Chrome + chrome-headless-shell (~531 MB measured); the builder stage installs all devDependencies; the binaries can't even run on the alpine (musl) base. Its only consumer is `test-console.cjs` (a local debug script).
- **Justification:** Every rebuild of the dependency layer pays the download and layer size for an unused tool.
- **Fix:** Remove puppeteer (and `test-console.cjs`) from the project, or set `PUPPETEER_SKIP_DOWNLOAD=1` in the builder stage.

### [BEST-VIOLATION][Medium] docker-build.sh:17,21-27 — pre-build teardown leaves the service offline on failure, and `chmod -R 777 ./data`
- **Details:** `docker stop`/`rm`/`down -v` run before `up -d --build`, and `./data` (the bind-mounted persistent store) is set world-writable — while `rebuild-docker.sh:27` sets the same tree to 755/owner 1001.
- **Justification:** A failed build leaves the app down (the opposite of what `deploy.sh` documents), and the two scripts fight over `./data` permissions on every run; 777 lets any local user modify persisted data.
- **Fix:** Drop the pre-build teardown (compose recreates on `up -d --build`); set ownership once (`chown 1001:1001 ./data && chmod -R u+rwX ./data`), never 777.

### [BUG][Medium] vite.config.js:51,143,147 — backend port hardcoded in three places while the repo's own tooling tells devs to change it
- **Details:** The auth-plugin fetch and both proxy targets hardcode `http://localhost:3001`, while `kill-dev-servers.sh:18` instructs `PORT=3002` and `config.ts:13` reads `PORT`. `loadEnv` is called (line 96) but its result is unused.
- **Justification:** Following the printed advice breaks every `/api` call and the session check in dev.
- **Fix:** Read the port from the loaded env (`env.PORT ?? 3001`) into one constant used by the fetch and both proxies.

### [BUG][Medium] kill-dev-servers.sh:30-33 — pkill pattern can never match the real command line
- **Details:** `pgrep/pkill -f "nodemon backend/server.ts"` vs the actual `nodemon --exec tsx backend/server.ts`.
- **Justification:** The contiguous string never occurs, so the script silently fails to kill the backend dev server it exists for (and has no `tsx` pattern at all).
- **Fix:** Delete the script in favor of `concurrently -k`, or match the real command lines.

### [BUG][Medium] rebuild-docker.sh:26-27 — hardcoded data path contradicts the actual deploy root
- **Details:** `chown/chmod … /srv/dev/winner/data/` vs `deploy.sh:8 REMOTE_PATH="/srv/win/"`.
- **Justification:** The chown targets a nonexistent path, the error is ignored (no `set -e`), and the permission fix never happens on the real data directory.
- **Fix:** Derive the data path from the script's own directory and fail fast on chown errors.

### [FRAMEWORK-FIGHT][Medium] kill-dev-servers.sh — 78-line hand-rolled process killer duplicating `concurrently -k`, already rotted
- **Details:** `dev:all` already uses `concurrently -k`, which tears down both dev servers on exit.
- **Justification:** The script is redundant for the documented workflow and has drifted from reality (the pattern mismatch above).
- **Fix:** Delete it and rely on `concurrently -k`.

### [BUG][Low] tsconfig.json:19-21 — the include pattern matches zero files
- **Details:** `"include": ["src/**/*.ts"]` with `noEmit:false`/`outDir:./dist`, but `src` contains no `.ts` files (verified).
- **Justification:** `tsc -p tsconfig.json` fails with TS18003; the emit settings are inoperative dead config that misleads editors.
- **Fix:** Add `allowJs` with correct includes, or reduce it to an editor-only `noEmit:true` config.

### [FRAMEWORK-FIGHT][Low] nodemon.json:5 — `exec: ts-node` is dead config overridden by the dev script's `--exec tsx`
- **Details:** The CLI `--exec tsx` overrides `nodemon.json`; the ts-node runner, its tsconfig block, and the ts-node dependency are all unused.
- **Justification:** Editing `nodemon.json`'s exec has no effect — a confusing trap; `tsx` has built-in watch, so nodemon is redundant too.
- **Fix:** Standardize on `tsx watch backend/server.ts` and drop the nodemon/ts-node config and dependencies.

### [BEST-VIOLATION][Low] Dockerfile:63-64 vs docker-compose.yml:16-21 — duplicated healthcheck with contradictory start periods
- **Details:** Dockerfile `--start-period=5s` vs compose `start_period: 40s`; compose wins.
- **Justification:** Two sources of truth that have already drifted.
- **Fix:** Keep the healthcheck only in `docker-compose.yml`.

### [BEST-VIOLATION][Low] pnpm-workspace.yaml + vite.config.js:79 — pnpm signals in an npm-managed repo
- **Details:** `node_modules` is npm-managed (verified) and the Dockerfile uses npm, yet a pnpm workspace file is committed and the dev error page instructs `pnpm dev:all`.
- **Justification:** A developer who follows the instruction produces a second, differently-resolved dependency tree (no lockfile exists for either manager).
- **Fix:** Pick one manager (add `packageManager` + commit its lockfile) and remove the other's config and on-screen instructions.

### [BEST-VIOLATION][Low] test-console.cjs, test-texting.html — tracked debug debris in repo root, rsynced to the server
- **Details:** Both are git-tracked; `test-texting.html` fires a real `./api/texting` `sendMessage` if served. `deploy.sh` has no exclude for them.

### [BOTTLENECK][Low] package.json:59,61 — frontend-only scanner libraries installed into the production server image
- **Details:** `qr-scanner` and `zxing-wasm` are in `dependencies` (installed by `npm install --omit=dev`) but imported only by frontend code that Vite bundles into `dist`.

### Cross-cutting themes
1. **Silent failure over fail-fast** — `writeCollection`, `getFromStore`, `batchFetch`, and the Svelte `client.get()` all swallow errors and return empty/`false`, masking outages as "no data" and, in one path, enabling a destructive hard-delete. This directly contradicts the project's stated fail-fast rule.
2. **Unsynchronized read-modify-write** on whole-JSON collections recurs at all three data touchpoints (routes, service, browser) with no locking or field-level updates — the root of several data-loss findings.
3. **The Svelte app is a partially-wired rewrite** — a large share of its settings persist with no runtime consumer and several components are never mounted; treat it as incomplete, not merely buggy.
4. **Config depends on unset-defaulting `NODE_ENV`** for both rate limiting and the cookie `Secure` flag — one missing env var silently disables two security controls.
5. **Deploy/build scripts lack `set -e`** and verify liveness by grepping `docker ps`, so failed builds report success while production serves a stale image.
